## Context

評価関数は `source/eval.d` の `staticValue(const ref Position)` 1つで、`search.d` と `text.d` から呼ばれる。現在は NNUE 版で、過去の版は `source/eval.d.nanoha_mini` などの名前でソースツリーに残してある（`.d` 以外の拡張子なのでビルドされない）。
`Position.board` の添字は pp.bin の盤面アドレス（図1）と一致する。

## Goals / Non-Goals

**Goals:**
- `staticValue` のインターフェースを変えずに PP 評価関数に置き換える
- 動作確認用、かつ学習の初期値として使える pp.bin を用意する

**Non-Goals:**
- 差分計算（doMove ごとの増分更新）
- 学習器（別途仕様を作る）
- ビッグエンディアン環境への対応

## Decisions

### NNUE 版を `eval.d.nnue` として残し、`eval.d` を PP 版に置き換える
既存の慣習（`eval.d.nanoha_mini` など）に合わせる。切り替えはファイルのコピーで行う。
代替案：バージョン指定（`version`）で切り替える → 2つの評価関数が1ファイルに混ざるので採らない。

### pp.bin は `__gshared short[2344][2344]` に一括で読み込む
10.9MB の配列に `rawRead` で読み込む。読み込む前に `File.size` が 10,988,672 であることを確かめる。リトルエンディアンの環境ではバイト順の変換は不要。
代替案：対称性を使って半分だけ持つ → 表引きの添字計算が増えるので採らない。メモリは十分小さい。

### 駒リストのインデックスは2つのオフセット表から作る
- 盤上の駒：`OFFSET_PP[Square.i] + i`（`Square.i` で引く29要素の表。玉を含む）
- 持ち駒：`OFFSET_HAND[color][type] + k`（k は 0 から数える）

駒リストの長さは最大40。

### 毎回すべて計算する
`sum_{i<=j}` は最大 820 回の表引きで、十分軽い。差分計算は速度が問題になってから考える。

### 和は int で計算し、FV_SCALE = 16 で割る
和の最大値は 820 × 32767 ≒ 2,700万なので int32 に収まる。FV_SCALE を 16 にすれば、対角に龍の駒割り（1164 × 16 = 18624）も入る。

### `misc/pp_init.rb` で対角だけに駒割りを入れた pp.bin を作る
対角に駒の価値 × 16 を入れ、ほかを 0 にする。駒の価値は `eval.d.nanoha_mini` の `P_VALUE` を使う。持ち駒の価値は成る前の駒と同じとし、玉は 0 とする。後手の駒は符号を反転するので、先後対称と行列の対称を満たす。
評価器の動作確認と、学習の初期値の両方に使う。既存の `misc/*.rb` に合わせて Ruby で書く。

## Risks / Trade-offs

- [学習した値が大きすぎると、E ÷ 16 が short に収まらず、キャストで値が壊れる] → debug ビルドの assert で検出する。学習器で値を抑える
- [差分計算をしないので NNUE 版より NPS が変わる] → PP は NNUE より計算量が小さいので許容する。遅ければ差分計算を別の変更で入れる
- [ビッグエンディアン環境では値を正しく読めない] → 対象外とする

## Migration Plan

pp.bin を作業ディレクトリに置いて実行する（`*.bin` は .gitignore 済み）。NNUE 版に戻すには `eval.d.nnue` を `eval.d` にコピーしてビルドし直す。
