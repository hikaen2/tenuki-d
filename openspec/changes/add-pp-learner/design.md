## Context

評価関数は `source/eval.d` の PP 版（add-pp-eval）。pp は起動時に pp.bin から `__gshared` 配列に読み込まれ、`staticValue` が駒リストを作って `i<=j` の和を返す。
対局用の探索 `search.d` は時間制限・置換表・スレッドを使い、`search.d` と `tt.d` はモジュールの静的コンストラクタでスレッドの起動や 268MB の確保を行う。
学習に必要なモジュール（types, zobrist, parser, position, movegen, text, eval）は search, tt, book, main に依存しない。
マシンは 8 コア、メモリ 15GB。

## Goals / Non-Goals

**Goals:**
- `tenuki` 本体の振る舞いを変えずに、学習器を別の実行ファイルとして作る
- pp.bin 1つで学習の状態を表し、いつでも止めて再開できるようにする

**Non-Goals:**
- floodgate からの自動ダウンロード
- float の重みや AdaGrad などの更新方法
- 正則化や駒割りの拘束（必要になったら別の変更で入れる）
- 学習の分散実行

## Decisions

### 学習器は dub の別構成としてビルドする
`dub.json` に `learn` 構成を追加し、`source/learn.d` を main にして search.d, tt.d, book.d, main.d を除く。`dub build -c learn -b release` で `tenuki-learn` を作る。既定の構成からは learn.d を除く。
代替案：`tenuki learn ...` のようにサブコマンドにする → search と tt の静的コンストラクタがスレッドと 268MB を確保してしまうので採らない。

### eval.d から駒リスト作成と pp を公開する
`staticValue` の中の駒リスト作成を関数に切り出して公開し、pp 配列も公開する。学習器はこの pp を直接書き換え、探索の評価には `staticValue` をそのまま使う。こうすれば、学習中の評価と対局時の評価が必ず一致する。
pp.bin の読み込みは静的コンストラクタから `loadPP(path)` に切り出し、`tenuki` 本体は静的コンストラクタから `loadPP("pp.bin")` を呼ぶ。学習器は eval を import するが、静的コンストラクタで作業ディレクトリの pp.bin を読まないようにし、引数で受け取ったパスを `loadPP` に渡す。
代替案：学習器に評価関数を別に書く → 2つの実装がずれるおそれがあるので採らない。

### 学習用棋譜は Ruby スクリプトで作る
`misc/csa2kifu.rb` が floodgate の CSA ファイル群を読み、平手・レーティング・投了で選んで、1行1局のテキストにする。平手の判定は、`PI` 行、または `P1`〜`P9` 行が平手の初期配置と一致することで行う。レーティングは `'black_rate:` と `'white_rate:` のコメント行から読む。
学習器側は、平手の初期局面から既存の `parseMove` で指し手を適用するだけにする。
代替案：学習器で CSA ファイルを直接読む → 選別の条件を変えるたびに D を書き直すことになるので採らない。

### 浅い探索は学習器の中に書く
1手指した局面から、駒を取る手（`capturelMoves`）だけの alpha-beta で静止探索する。静止探索は 4 手までは駒を取る手をすべて読み、それより深いところでは直前の手が動いた升で取り返す手だけを読む（tanuki- と同じ考え方）。1つの升の取り合いは駒が尽きれば終わるので、深さの上限は要らない。手番側は「取らない」こともできる（stand pat）。
代替案：search.d と同じく 4 手で打ち切る → 取り合いの途中の局面が末端になり、駒割りの誤差を2駒の関係で埋める学習になるおそれがあるので採らない。Bonanza のように SEE で枝刈りする → SEE を新しく書く必要があるので、遅かったときに検討する。読み筋は配列で返し、その末端の局面から駒リストを作る。
候補の手は `legalMoves` が返す手とする。これは擬似合法手で、王手放置や打ち歩詰めを含む。王手放置の手は静止探索で玉を取られて ±15000 になり窓の外に出るので、勾配には寄与しない（±15000 の末端は pp の和ではないので、そもそも勾配を持たない）。
棋譜の手 m* は全幅で探索して v(m*) を決め、それ以外の手は窓 [v(m*) - 256, v(m*) + 256] で探索する（Bonanza の FV_WINDOW）。窓の外に出た手は勾配が 0 なので、読み筋を保存しない。

### 1 iteration を探索と更新に分ける
Bonanza の Parse1 / Parse2 にならう。

```
iteration:
  探索段階  全局面・全合法手を探索し、窓の中の手の読み筋（指し手列）を保存する。J もここで求める
  更新段階  step 数だけくり返す:
              保存した読み筋を局面 p から doMove で再生し、末端を staticValue で評価し直す
              勾配を求め、対称性でまとめて ±1 更新する
```

±1 の更新は FV_SCALE=16 の単位なので、探索1回に更新1回では評価値がほとんど動かない。読み筋を固定して更新を step 回まわすことで、重い探索の回数を減らす。
読み筋は指し手列だけを保存し、局面 p は棋譜の手を平手から再生して作る（末端の駒リストを持つより小さい）。step の途中で窓の中に入ってきた手は、次の iteration の探索段階まで無視する。
読み筋は Bonanza の tmp.bin と同じく、pp.bin と同じ場所の `pp.bin.pv` に1局ずつ書き出し、更新段階では step ごとに先頭から1局ずつ読み直す。1局分は、局面ごとに棋譜の手・読み筋の数・読み筋（手数と手の列）を並べた uint16 の列。棋譜ファイルも探索段階と一致率の計算のたびに CHUNK（4096）局ずつ読み直すので、メモリは局数によらない。`pp.bin.pv` は学習の終わりに消す。
代替案：末端の駒リストを保存する → 1万局で数 GB になるので採らない。読み筋をメモリに持つ → 1000 局で約 0.85 GB、1万局では 15GB に収まらないので採らない。

### 勾配の計算
局面 p の手番側から見て、leaf(m) の評価値は先手視点の E に符号 s（p が先手番なら +1、後手番なら -1）を掛けたもの。leaf(m) の駒リストに含まれる `i<=j` のペア (a,b) ごとに、

```
d = a * T(x) * (1 - T(x))   x = v(m) - v(m*)
g[leaf(m) のペア]  += s * d / 16
g[leaf(m*) のペア] -= s * d / 16
```

を足す（16 は FV_SCALE）。符号しか使わないので、定数倍は省いてよい。|x| >= 256 なら d = 0 とする（窓の外）。

### 並列化
CHUNK 局ずつ読んだ対局をスレッドに分ける（探索段階・更新段階・一致率の計算のいずれも1局単位）。対局の長さはまちまちなので、CHUNK はスレッド数（192 コアのマシンも想定）より十分大きくして、CHUNK ごとの待ち合わせを減らす。CHUNK 局分の棋譜と読み筋は合わせて 200MB 程度。スレッドごとに int64 の勾配配列（2344 × 2344 × 8B = 44MB）を持つ。8 スレッドで 352MB。step の終わりに全スレッドの勾配を足し合わせてから更新する。pp は各段階・各 step の途中では読むだけなので、ロックは要らない。
勾配は d を固定小数点（d × 2^20 を丸めた整数）にして足す。整数の和は足す順番によらないので、スレッド数を変えても同じ pp.bin になる。
代替案：float で足し、足す順番を固定する → 打ち消し合って 0 になるはずの勾配が丸め誤差で ±ε になり、スレッド数によって符号が変わるので採らない。

### 対称性でパラメータをまとめる
ペア (a,b) に、入れ替え・inv・mir を組み合わせた最大 8 通りの変換をかけたものを1つのグループとし、各ペアにグループ内での符号（inv を奇数回かけたら -1）を付ける。
- 勾配：グループ内の各ペアの勾配に符号を掛けて合計する
- 更新：合計の符号で代表値を ±1 し、グループ内のすべてのペアに符号を掛けて書き戻す
- 同じペアが +1 と -1 の両方の符号で現れるグループ（例：(a, inv(a)) で mir(a) = a）は 0 に固定する

グループの表は起動時に1回だけ作る。

### pp.bin の書き出し
`pp.bin.tmp` に書いてから `rename` で置き換える。

## Risks / Trade-offs

- [探索段階が重い。1万局 × 120 局面 × 80 手の静止探索で、8 スレッドでも数十分かかる] → 窓で枝を刈り、1回の探索を step 回の更新に使う。棋譜の数を引数で指定できるようにし、まず 1000 局程度で動作と一致率の上昇を確かめる
- [step の間は読み筋が固定なので、step 数を大きくすると、更新後の pp では別の読み筋が選ばれるずれが大きくなる] → step 数を引数にして、一致率を見ながら決める
- [±1 の更新は遅く、値が大きく動くまでに多くの step が要る] → 初期値の対角に駒割りが入っているので、大きく動かす必要があるのは主に2駒の関係。遅すぎれば更新方法だけ差し替える
- [保存する読み筋の大きさ] → ファイルに書くのでメモリは局数によらない。そのかわり局数に比例したディスク容量を使い、step ごとにファイルを読み直す
- [正則化がないので、出現の少ないペアの値が偏るおそれ] → 一致率と対局で確かめ、問題があれば別の変更で正則化を入れる
- [floodgate の CSA の書式の揺れ（コメント、時間、終局の表記）] → 選別の段階で解析できない対局を除き、件数を表示する

## Migration Plan

1. floodgate の棋譜アーカイブ（`wdoor*.7z`）を手動でダウンロードして展開する
2. `ruby misc/csa2kifu.rb <最低レーティング> <CSA ファイル群> > games.txt` で学習用棋譜を作り、一部を検証用に分ける
3. `ruby misc/pp_init.rb > pp.bin` で初期値を作る
4. `./tenuki-learn train.txt test.txt pp.bin <iteration 数> <step 数>` で学習する
5. 学習した pp.bin を `tenuki` の作業ディレクトリに置いて対局する

## 試運転の結果

floodgate 2026 のレーティング 3500 以上の棋譜から、学習用 998 局（153,747 局面）、検証用 99 局（13,622 局面）で 10 iteration 学習した（初期値は `pp_init.rb`、8 スレッド）。

| step 数 | 一致率 iter 0 → 10 | J iter 1 → 10 | 1 iteration | 最大メモリ |
|---|---|---|---|---|
| 1 | 0.2239 → 0.2558 | 2,848,601 → 2,244,686 | 約 540 秒 | 655 MB |
| 4 | 0.2239 → 0.2698 | 2,848,601 → 1,563,060 | 約 535 秒 | 916 MB |
| 16 | 0.2239 → 0.2969 | 2,848,601 → 910,062 | 560〜690 秒 | 870 MB |
| 32 | 0.2239 → 0.3095 | 2,848,601 → 610,730 | 590〜830 秒 | 839 MB |
| 64 | 0.2239 → 0.3096（最高 0.3116、iter 8） | 2,848,601 → 384,700 | 650〜1240 秒 | 843 MB |

- J は各 iteration の更新前（探索段階）の値、一致率は更新後の値。iteration 1 の J は初期値の pp の値なので、step 数によらず同じ
- 時間はほぼ探索段階で決まり、step 数 16 でも 2 割増し程度
- step 数 1 は一致率が 0.255 前後で止まる。16・32 は 10 iteration 目でもまだ上がっている
- step 数 64 は iteration 8 で一致率が頭打ちになり、そのあと下がる。J（探索し直した値）は下がり続けているので、読み筋が古くなる影響ではなく、1000 局への過学習と考えられる
- 同じ時間で比べると step 数が大きいほうが一致率が高い（約 5000 秒で 16: 0.29、32: 0.30、64: 0.31）
- 1 iteration の時間は iteration が進むと短くなる。窓に入る手が減り、保存する読み筋と更新の量が減るため
- メモリは主に保存した読み筋。全 14,468 局では 10 GB を超える見込み
